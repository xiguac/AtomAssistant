# 原子助手 AtomAssistant · 架构方案 v0.2

> 定位：一个 7×24 常驻云端、事件驱动、带持久化记忆的个人/商务智能体运行时。
> 手机 App 是它的管理与通知终端，不是主体。

---

## 0. 一句话架构

**把助手做成一个"智能体操作系统"**：任务 = 进程，记忆 = 分级存储，MCP 工具 = 系统调用，
事件总线 = 中断，调度器 = 内核，任务结束产出的摘要 = 可回溯的日志。

你提的想法（事件驱动线程、短/长期记忆、数据复用与释放、结束后留摘要、标签分类）本质上就是
进程管理 + 分级存储 + 资源引用计数。这套抽象可以直接落到工程上，也是这个项目区别于
"套壳 Agent 框架"的核心。

### 已确认的产品形态（约束整个架构）

| 维度 | 决定 | 对架构的硬性影响 |
|---|---|---|
| 部署 | **用户自部署在自己的服务器**，单用户单实例 | 不能依赖 K8s/Kafka 这类重组件，必须能 docker-compose 单机跑起来；不做多租户隔离层 |
| 用户 | **个人为主**，可加好友组成团队协作 | 协作是**实例之间的联邦直连**（用户服务器有公网 IP，走开放协议），不是同库多租户 |
| 共享 | 只共享**工作域**内容，`personal` 域**零外泄** | **域（生活/工作）是数据模型的一等字段**，域决定默认可见性；不确定时一律按私人处理 |
| 地域 | 主要面向国内用户 | 连接器优先国内生态 |
| 模型 | 走 API，**用户自行配置** | LLM 层必须是纯 provider 抽象，不绑定任何一家；密钥由用户持有 |
| 客户端 | iOS + Android 双端，**React Native** | 服务端只提供 BFF + 推送，UI 逻辑不进服务端 |
| 顺序 | 服务端 → MCP 市场 → Skill 自装 | 市场与 Skill 是 P4 之后的事，但**权限模型必须在 P0 就预留** |

**自部署带来的最大约束**：目标机器可能只有 2C4G。整套系统的常驻内存要控制在 1GB 以内，
这直接否掉了"每个任务一个常驻进程"的做法，也是 §3.3 持久化状态机设计的另一个理由。

## 1. 技术选型

### 1.1 服务端语言：Go（推荐）

**结论：主服务用 Go，全栈单语言，不引入 Python/Node 侧车。**

理由（按权重排序）：

1. **常驻进程是 Go 的主场。** 单二进制、内存占用可预测、容器体积小、崩溃恢复与滚动升级简单。
   7×24 跑几百上千个并发长任务，Go 的运维成本最低。
2. **负载是 I/O 密集，不是 AI 计算密集。** 我们不训练模型、不跑本地推理，只是并发调用
   第三方大模型 HTTP/SSE 接口和 MCP 工具。goroutine + channel 天然适配，Python 的
   AI 生态优势在这里基本用不上。
3. **"Go 的 AI 生态薄"对本项目不是缺点。** 你明确要求自研而不是缝合 LangChain/LlamaIndex 之类。
   Go 缺框架反而逼出干净的自研内核；真正需要的只有 HTTP client、JSON Schema、向量检索，
   都不依赖 AI 生态。
4. **定时与任务队列成熟。** Postgres 驱动的任务队列（River）、Temporal 官方 Go SDK 都可选，
   不必自己造分布式调度。
5. **MCP 有官方 Go SDK**（modelcontextprotocol/go-sdk），社区还有 mark3labs/mcp-go。
   *这一条我没有实测过当前版本的成熟度，选型落地前需要自己验证。*

### 1.2 被否掉的选项，以及为什么

| 语言 | 优势 | 否掉原因 |
|---|---|---|
| **Elixir/OTP** | 概念上最贴合：GenServer = 任务进程、Supervisor = 崩溃自愈、进程隔离天然。你描述的"事件驱动线程"几乎就是 OTP 的原话 | MCP/LLM 生态薄、人才稀缺、调试链路陌生；Go 用"持久化状态机"能拿到 90% 的等价能力，剩下 10% 不值这个代价 |
| **TypeScript/Node** | MCP 官方 SDK 最完整、AI SDK 最好用、可与 App 共享类型 | 单线程模型跑长任务要靠进程池硬凑；内存占用高；长时间常驻的稳定性不如 Go |
| **Python** | AI 生态最强 | 7×24 常驻 + 高并发 + 部署，恰好是它最差的三个方向。为了用不上的生态付全程代价 |
| **Rust** | 性能与可靠性天花板 | 迭代速度慢一个量级，早期产品形态还会大改，而性能根本不是瓶颈 |

**如果将来确实需要 Python**（本地 embedding、重排模型、OCR），做成独立的无状态推理服务，
gRPC 调用，绝不让它进主链路。

### 1.3 存储与中间件

| 组件 | 选型 | 说明 |
|---|---|---|
| 主库 | PostgreSQL 16+ | 任务、记忆、实体、审计、连接器数据全在一个库，事务一致 |
| 向量检索 | pgvector | 初期不引入独立向量库，数据量到千万级再考虑迁移 |
| 缓存/短期态 | Redis | 会话态、限流、分布式锁、热数据 |
| 队列/调度 | River（Postgres 队列）起步 | 少一个中间件就少一份 7×24 运维负担；量级上来再换 NATS JetStream |
| 对象存储 | S3 兼容 | 附件、快照、大摘要 |
| 推送 | APNs / FCM | 独立通知服务，带重试与免打扰策略 |

**关于 Temporal**：它能直接解决长任务的持久化执行与重放，但自建 Temporal 集群对早期是重资产。
本方案选择**自研持久化步骤日志（见 §3.3）**——大约 1500~2000 行，换来的是任务状态与业务数据
同库可查、可 SQL 排障、可自定义调度策略。若后期觉得吃力，可平移到 Temporal，抽象是兼容的。

## 3. 内核：事件驱动的任务进程模型

### 3.1 进程类比对照表

| 操作系统 | 原子助手 | 说明 |
|---|---|---|
| 进程 | **Task（任务）** | 一次有目标、有生命周期的工作单元 |
| PCB 进程控制块 | **TCB 任务控制块** | Postgres 一行记录，含状态/优先级/预算/资源句柄 |
| 线程 | **Step（步骤）** | 任务内的一次推理或一次工具调用 |
| 子进程 | **Subtask** | 可并发、可 fork/join |
| 中断 | **Event** | 定时、Webhook、用户消息、工具回调 |
| 系统调用 | **MCP Tool Call** | 唯一的对外副作用出口，统一审计 |
| 内存 | **短期记忆 + 数据租约** | 任务结束释放 |
| 磁盘 | **长期记忆** | 跨任务持久 |
| 日志 | **任务摘要 Episode** | 结束后压缩留存，可回溯 |

### 3.2 任务状态机

```
   NEW ──▶ READY ──▶ RUNNING ──┬──▶ DONE
            ▲   ▲              │
            │   └── WAITING ◀──┤   (等时间/等审批/等外部回调/等子任务)
            │                  │
            └──── SUSPENDED ◀──┴──▶ FAILED / CANCELLED
```

- **WAITING 是核心状态**：长程任务 90% 的时间在等。等待中的任务**不占运行时资源**，
  只是一行数据库记录 + 一个唤醒条件（时间戳 / 事件订阅 / 回调 token）。
- **SUSPENDED**：预算耗尽、依赖不可用、用户手动暂停。
- 每次状态迁移写审计，可在 App 上完整回放。

### 3.3 持久化执行（关键设计）

**任务的真身是数据库里的状态机，不是内存里的 goroutine。**

```
task_steps 表（append-only 步骤日志）
  task_id | seq | type(llm|tool|wait|branch) | input_hash
          | output | tokens | cost | started_at | ended_at | status
```

- 每个 Step 执行前写入 `pending`，成功后写 `done` 并记录输出。
- 进程重启/宕机后，调度器扫描 RUNNING 且心跳超时的任务 → 从最后一个 `done` 的 seq 续跑。
- 工具调用带**幂等键**（由 `task_id + seq` 派生），保证重放不会重复下单、重复打车。
- 这同时免费拿到：成本核算、性能分析、失败重试、以及给用户看的"AI 到底干了什么"时间线。

### 3.4 调度器

按以下维度排队与限流：

- 用户级并发上限（防止单个用户打满集群）
- 工具级并发与速率（第三方 API 配额）
- 优先级：用户前台交互 > 有 deadline 的任务 > 后台整理类任务
- 预算：每个任务有 token / 金额 / 墙钟时间三重上限，超限转 SUSPENDED 并推送用户

### 3.5 事件总线

事件类型：`schedule.tick`、`connector.changed`、`user.message`、`tool.callback`、
`task.finished`、`memory.conflict`。

任务用**订阅表达式**声明唤醒条件（如 `calendar.event.created AND attendee.contains(客户A)`），
避免"每分钟全量轮询"这种蠢办法。

### 3.6 全局决策器（Global Planner）

一个独立的低频常驻任务，不属于任何单个任务：

- 定期纵览：所有活跃任务 + 日程 + 未读事件 + 长期记忆
- 输出：任务优先级重排、冲突检测（两个任务都要占用周三下午）、主动建议、日程整理、
  该拆分/合并/取消哪些任务
- 它是"AI 纵观全局做决策"的落点，而不是让每个任务自己乱抢资源

## 4. 记忆系统

### 4.1 四级分层

| 层级 | 名称 | 作用域 | 存储 | 生命周期 |
|---|---|---|---|---|
| **M0** | 上下文工作区 | 单次推理 | 内存 | 秒级，用完即弃 |
| **M1** | 任务短期记忆 | 单个任务 | Redis + PG | 任务结束即释放 |
| **M2** | 长期记忆 | 用户级 | PG + pgvector | 永久，可编辑可遗忘 |
| **M3** | 情景归档 | 用户级 | PG + S3 | 永久，冷数据 |

**M1 → M2/M3 的落幕流程（任务结束时）**：

```
任务 DONE
  ├─ 生成 Episode 摘要（做了什么/结果/耗时/花费/关键决策）→ M3
  ├─ 提炼记忆候选（偏好、实体事实、可复用流程）→ 记忆写入管线 → M2
  ├─ 释放数据租约（引用计数 -1，归零的缓存数据可被 GC）
  └─ M1 数据标记可删（保留 N 天冷却期，防止误删后无法追溯）
```

### 4.2 长期记忆的五种类型

不要把所有东西一股脑塞进向量库。分类型建模，检索策略才能不同：

1. **偏好记忆 Preference —— 必须是条件化规则**
   这是你举的打车例子，也是最容易做砸的地方。不能存成"用户喜欢便宜的车"：
   ```
   subject: user
   domain:  出行/打车
   condition: {场景: 个人通勤}   → value: {车型: 顺风车, 优先: 价格}
   condition: {场景: 接待客户}   → value: {车型: 豪华型, 优先: 体验}
   confidence: 0.9 | source: task#123 | updated_at | hit_count
   ```
   检索时先解析当前场景，再匹配条件；条件冲突按 特异度 > 置信度 > 时间新近 排序。

2. **实体档案 Entity Profile** —— 客户、同事、家人、常去地点、常买商品
   ```
   entity: 客户张总
   attrs:  {口味偏好: 川菜/重辣, 忌口: 海鲜过敏, 关注产品线: 工业级传感器,
            称呼习惯: 张总, 联系时段: 工作日下午}
   每个 attr 独立带 source / confidence / updated_at
   ```
   忌口这类**安全相关属性要打高优先级标记**，任何涉及餐饮的任务强制注入，
   不走相似度检索（相似度召回失败一次就是事故）。

3. **语义事实 Semantic Fact** —— "公司报销上限 500"、"护照 2027 年到期"

4. **程序记忆 Playbook** —— 从成功任务里沉淀的可复用流程（"接待客户标准流程"）

5. **情景摘要 Episodic** —— M3 的索引投影，供"上次给张总送礼送的什么"这类回溯

### 4.3 记忆写入管线（防止记忆污染）

```
候选提取 → 去重(语义相似) → 冲突检测 → 置信度评估 → 写入/更新/降权
                                │
                                └─ 高风险冲突 → 推送 App 让用户裁决
```

- **不做无脑追加**。同一事实反复出现 → 提升置信度；出现矛盾 → 保留两条并标注时间线，
  由新近性和用户裁决决定生效值。
- **遗忘机制**：长期未命中 + 低置信度 → 降权 → 归档。防止记忆库无限膨胀污染检索。
- **用户可见可控**：App 里必须能查看/编辑/删除任意一条记忆。这是信任的前提，不是加分项。

### 4.4 上下文装配：渐进式披露

**原则：永远不把当前事物一股脑丢给模型。按关联度分环下发，低关联的只给索引，让模型自己按需展开。**

这不只是省 token。长任务跑几天后，相关材料的总量必然远超任何上下文窗口，
"全塞进去"在物理上就不成立；而且无关信息会稀释注意力，直接降低决策质量。

#### 四环模型

| 环 | 内容 | 形式 | 预算占比 |
|---|---|---|---|
| **L0 必达** | 任务目标、当前状态、最近 N 步、**安全类属性**（过敏/禁忌/红线） | 原文，不可裁剪 | ~25% |
| **L1 高关联** | 直接命中的记忆、当前步骤要用的数据、命中的偏好规则 | 原文 | ~40% |
| **L2 中关联** | 相关实体档案、相关历史 Episode、同域记忆 | **摘要形式** | ~25% |
| **L3 低关联** | 其余候选 | **只给一行索引**：`[mem_8f21] 客户张总·送礼偏好（2026-03，置信0.8）` | ~10% |

**关键机制**：L3 不是被丢弃，而是以目录形式在场。模型看到目录后可主动调用
`context.expand(id)` 把某条拉成原文，或 `context.search(query)` 做二次检索。
**把检索权交给模型，而不是由我们一次性预填**——这才是渐进式披露的工程形态。

展开有配额（如单步最多 5 次、总 token 不超预算），防止模型无限展开把窗口撑爆。

#### 关联度打分

不是纯向量相似度。混合打分：

```
score = w1·向量相似度
      + w2·标签重合度(domain/scene/entity)
      + w3·实体精确命中     ← 权重最高，"张总"命中就该排前面
      + w4·时间新近性衰减
      + w5·历史命中率(hit_count，被证明有用的记忆更容易再被用到)
      - w6·置信度惩罚(低置信记忆降权)
```

安全类属性走**旁路强制注入**，不参与打分、不参与裁剪。相似度召回失败一次就是事故。

#### 长任务的上下文压缩

任务持续几天、几十上百步时，步骤日志本身就超窗口。三段式：

```
[任务级摘要]  目标、已确认事实、已排除路径、关键决策及理由   ← 长期稳定，低频重写
[阶段级摘要]  当前阶段做了什么、卡在哪                      ← 每阶段结束时生成
[最近 N 步]   原文                                          ← 滚动窗口
```

**"已排除路径"必须显式记录**，否则长任务会反复尝试同一条死路——这是长程 Agent 最常见的失败模式。

### 4.5 记忆冲突与修正

记忆必须可修正，且修正过程要让用户看得见。**新信息不等于正确信息**，直接覆盖是错的。

#### 冲突分类

| 类型 | 例子 | 默认处理 |
|---|---|---|
| **时效更替** | 住址从 A 变 B | 新值生效，旧值加 `valid_until` 转历史，不算冲突 |
| **真实矛盾** | 上月"张总忌海鲜"，本月"张总点了海鲜" | **触发仲裁** |
| **范围重叠** | "打车要便宜" vs "接待客户打豪华车" | 不是冲突，是**条件特异度不同**，两条共存 |
| **来源可信度差** | 用户口述 vs 连接器同步的权威数据 | 权威数据优先，但标注差异 |
| **观察 vs 陈述** | 用户说不吃辣，但订单记录连续点川菜 | 保留两条，向用户求证 |

#### 仲裁流程

```
新记忆候选
  ↓
定位同 subject+domain+condition 的既有记忆
  ↓
冲突分类（LLM + 规则）
  ↓
【交叉验证】用其他记忆和历史 Episode 佐证/反驳
   例：新说法"张总不忌海鲜"
       → 检索到 task#88 摘要"因客户海鲜过敏改订川菜，客户当场确认"
       → 旧记忆有强佐证，新说法可信度存疑
  ↓
分级处置
  ├─ 新证据充分 → 直接更新，事后在 App 汇总里告知
  ├─ 证据相当   → 保留双值，标记 disputed，下次相关任务前询问
  └─ 旧记忆有强佐证 / 涉及安全属性 → 主动向用户对质
```

#### 对质与"用户执意覆盖"

助手要**明确指出矛盾和出处**，而不是默默接受：

> 记录里张总海鲜过敏（来源：3月12日接待任务，当时客户本人确认）。
> 你现在说可以点海鲜，是情况变了，还是我记错了？

用户执意 → **新值立即生效并覆盖**，但：

1. **不物理删除旧值**，写入版本链，标记 `superseded_by` 和 `override_reason: user_explicit`
2. 用户显式指定的记忆置信度置为 1.0，且**后续同类冲突不再重复对质**（避免助手变成复读机）
3. 安全类属性（过敏、疾病、财务红线）的覆盖，在 App 上需要二次确认，并永久保留原记录

#### 数据模型：记忆是有版本链的

```
memories            id, user_id, type, subject, domain, condition,
                    current_revision_id, status(active|disputed|expired|archived),
                    confidence, tags, embedding

memory_revisions    id, memory_id, value, source(task_id|user|connector),
                    evidence[], confidence, created_at,
                    superseded_by, override_reason
```

`memory_id` 稳定，值随 revision 演进。好处：可回溯"助手当时为什么那么判断"、
可一键回滚误覆盖、可向用户展示完整的认知变化过程。

### 4.6 记忆的时效性

**每条记忆在写入时必须判定时效类型，没有默认永久这一说。**

| 类型 | 例子 | 处理 |
|---|---|---|
| **永久** | 血型、海鲜过敏、生日 | 无过期，变更需强证据 |
| **长期可变** | 住址、职位、常用车型偏好 | 无硬过期，但置信度随时间缓慢衰减，超过阈值触发复核 |
| **限时** | "本月预算还剩 2000"、"下周在上海出差"、"项目 A 进行中" | **必须有 `valid_until`**，到期自动退出检索 |
| **一次性** | "帮我订今晚的餐厅" | 任务结束即失效，只留 Episode |

工程要点：

1. **抽取时就要输出时效字段**，不能事后补。LLM 抽取记忆候选的结构化输出里必带
   `temporality` 和 `valid_until`。
2. **相对时间一律转绝对时间**存储。"下周三"必须转成 `2026-09-16`，
   否则三个月后这条记忆就是错的。
3. **过期不等于删除**。过期记忆退出主检索，但保留在 M3，供"我上个月预算是多少"这类回溯。
4. **过期前主动提醒**：限时记忆临近到期且仍被频繁命中 → 询问用户是否延续。
5. 检索时**时间过滤先于相似度计算**，避免过期内容占用召回名额。

## 5. 标签与分类

统一的标签体系同时作用于 任务 / 记忆 / 实体 / 数据：

- **维度化标签**，不是扁平字符串：`domain:出行`、`scene:接待客户`、`entity:客户张总`、
  `priority:高`、`privacy:敏感`
- 来源：系统内置分类 + LLM 自动打标 + 用户手动修正（手动优先级最高）
- 用途：记忆检索域限定、任务路由、权限策略（`privacy:敏感` 的数据禁止进入某些模型）、
  统计视图（"这个月在客户接待上花了多少时间和钱"）

## 6. 数据平面：数据统一走 MCP，同步层只做副本与变更

数据获取有两条路径。**选哪条看数据源有没有稳定的开放协议，不看统一性。**

### 6.1 内建协议适配器（优先）

**有成熟开放协议的，直接连，不套 MCP。**

| 数据 | 协议 | 为什么不套 MCP |
|---|---|---|
| 邮件 | IMAP / SMTP | RFC 稳定几十年，Go 库成熟；**IMAP IDLE 能推送**，套一层 MCP 反而丢掉这个能力 |
| 日历 / 提醒 | CalDAV | 有 `sync-collection` 增量同步语义，比"定时全量拉 + diff"精确得多 |
| 通讯录 | CardDAV | 同上 |

套 MCP 会引入进程边界、序列化、schema 转换，以及对 MCP SDK 成熟度的依赖——
而这些协议是我们自己实现、自己控制两端的，统一带来的收益是零。

内建适配器跑在主进程内，不需要沙箱（是我们自己的代码），
但**必须走同一套数据出口管控、隐私分级和审计**。统一层是出口与审计，不是传输协议。

### 6.2 MCP 工具

**没有开放协议的第三方服务走 MCP**——滴滴、高德、美团这类。
MCP 不只是执行动作，**查询同样走它**，这类数据源的读取全部是 MCP 查询工具。

MCP 的价值在于：统一的能力发现、统一的权限声明、可通过市场分发、用户可自行安装。
对我们自己实现的 RFC 协议，这些价值都不存在。

### 6.3 同步层

需要被全局纵览的数据（日历、提醒、通讯录）落本地归一化副本：

```
内建适配器（增量同步语义）或 MCP 定时查询
  → 归一化落库
  → 差分产出 connector.changed 事件
```

不需要副本的（查天气、查路线、查单次订单详情）现场调用，不落库，也就没有隐私残留。

三个必须落副本的理由：

1. **事件驱动需要变更检测**。IMAP IDLE / CalDAV sync-collection 能做到近实时；
   只有 MCP 类数据源才需要退化成定时轮询 + diff。
2. **全局决策器要纵览全部数据**，每次现场查会慢、会打满第三方配额。
3. **长任务需要快照隔离**，跑三天的任务不能每次读到的数据都不一样。

### 数据复用与释放（保留）
- **租约机制**：任务声明需要哪些数据集 → 建立 lease（引用计数 +1）→ 任务结束释放。
  引用归零 + 超过保留期 → GC 可删。这正是你说的"数据复用 + 结束后释放"。
- **快照隔离**：长任务读到的数据要有版本，避免中途数据变了导致前后决策不一致。
- **最小权限**：连接器 scope 精确到读/写；token 加密存储，按用户隔离。

## 7. MCP 工具网关

- 统一管理多个 MCP Server（内置 + 用户自配），维护工具目录与 JSON Schema
- **风险分级**：`只读` / `可逆写` / `不可逆写（花钱、发消息、签合同）`
- **审批策略**：按风险 + 金额阈值决定 自动执行 / 执行后通知 / 执行前必须 App 确认
- **幂等 + 重试 + 熔断 + 审计**，每次调用完整留痕（谁、为什么、参数、结果）
- 后期可反向把原子助手自身暴露为 MCP Server，供其他客户端接入

---

## 8. LLM 路由层

- Provider 抽象层，屏蔽各家差异，支持随时换模型 / 多模型并存
- 按任务类型路由：规划用强模型，打标/摘要/抽取用便宜模型，长文走长上下文模型
- Prompt 组装、结构化输出校验、失败降级、成本核算到任务粒度
- 敏感数据标签决定可用模型集合

## 9. 移动端 App

核心不是聊天框，是**管理台**：

1. 收件箱：待审批操作、需要用户裁决的记忆冲突、任务异常
2. 任务视图：进行中 / 等待中 / 已完成，可看完整步骤时间线与花费
3. 日程视图：AI 整理后的日程 + 冲突提示
4. 记忆管理：浏览、搜索、编辑、删除记忆（信任基石）
5. 连接器与权限管理
6. 推送分级：必须打断 / 可延迟汇总 / 静默，带免打扰时段

## 11. 落地路线

| 阶段 | 目标 | 产出 |
|---|---|---|
| **P0** 内核骨架 | 任务能被创建、持久化执行、崩溃可恢复；**信任等级与可见性字段一次到位** | TCB + 步骤日志 + 调度器 + 数据模型 |
| **P1** LLM + MCP | 任务能真正调模型和工具，带审批与审计 | LLM 路由（用户自配密钥）+ MCP 网关 + 风险分级 + 数据出口管控 |
| **P2** 记忆系统 | 分层记忆、写入管线、冲突仲裁、时效管理、渐进式披露 | 偏好 / 实体两类先跑通 |
| **P3** 事件驱动 | 定时、Webhook、长等待唤醒 | 事件总线 + WAITING 全链路 |
| **P4** 数据平面 | 2~3 个国内连接器 + 租约与 GC | 日历 + 邮件优先 |
| **P5** App（RN 双端） | 推送、审批、任务时间线、记忆管理 | 可用的管理端 |
| **P6** 全局决策 | 跨任务纵览、日程整理、主动建议 | Planner 上线 |
| **P7** 协作联邦 | 加好友、共享工作事件、提议—应答排期 | 联邦直连协议 + 域约束与出站过滤器 |
| **P8** MCP 市场 | 工具发现、清单签名、沙箱安装 | 市场服务 + 本地沙箱运行时 |
| **P9** Skill 自装 | AI 提名、用户批准、能力受限执行 | Skill 运行时 + 完整安全闭环 |

两个关键节奏点：

- **P0 做扎实是整个项目成败的关键**。任务不能可靠地跑三天、断电后接着跑，后面全是空中楼阁。
- **P8/P9 排在最后不是因为不重要，而是因为它们把攻击面放大一个数量级**。
  前置条件是 P1 的沙箱和数据出口管控已经跑了足够久。详见 `安全模型.md`。
  但 P0 的数据模型必须预留 `trust_level` 与 `visibility` 字段，事后补是要重构全表的。

## 12. 主要风险

1. **记忆污染**：错误记忆会持续影响所有后续决策，且很难被发现。必须有置信度、来源、
   用户可编辑、可遗忘。
2. **不可逆操作**：AI 自动下单/转账/发消息出错的代价极高。审批策略要保守起步。
3. **成本失控**：长任务反复调用大模型。预算硬上限必须在 P0 就有。
4. **多任务竞争**：两个任务同时操作同一资源（同一个日程时段、同一笔预算），
   需要资源锁 + 全局决策器仲裁。
5. **隐私合规**：读取用户全域数据是这个产品的价值来源，也是最大的责任。
   数据分级、加密、可导出、可彻底删除。

## 13. 仍需拍板的问题

产品形态已确认，见 §0。剩下这几个会改变设计，不是细节：

### 已定

- **Skill 只做声明式，不含可执行代码。** 官方签名可自动安装，不可信来源需用户手动确认。
  防线放在**能力边界**（工具集取交集）而不是内容审查——理由见 `安全模型.md` §7.1。
- **联邦纯直连，不做中继。** 用户服务器有公网 IP，实例间走开放协议，协议规范公开。
  代价是每个实例都是公网端点，端口加固要求见 `协作与联邦.md` §2。
- **私人域零外泄，且不需要 free/busy 共享。** 排期用"提议—应答"完成：
  决策留在本人实例上，对外只回接受/建议改期，不暴露忙闲位图。

- **不可逆操作默认手动确认，用户可自设阈值**（金额、提前量、工具、域），
  但必须有单日/单任务累计帽子，且 untrusted 来源触发的动作不适用任何自动放行。
  详见 `截图理解与连接器.md` §5。
- **不引入 Temporal**，自研持久化步骤日志。开发资源与周期允许，且换来同库可查、可 SQL 排障。
- **首批连接器以 Apple 生态 + 截图为主**，截图理解是最高优先级入口。详见 `截图理解与连接器.md`。

### 尚未验证的技术点

1. iCloud 的 CalDAV/CardDAV/IMAP 端点、App 专用密码鉴权、限流策略 —— 需实测。
2. MCP 官方 Go SDK 的当前成熟度 —— 需实测。
3. 视觉模型对国内场景截图（微信通知、教务系统、订单页）的识别准确率 —— 需实测。
