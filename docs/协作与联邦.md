# 协作与联邦

> 前提：每个用户把原子助手部署在**自己的服务器**上，单用户单实例。
> 所以"加好友/组团队"不是同一个数据库里的多租户，而是**两个独立实例之间的通信**。
> 这个前提决定了本文所有设计。

---

## 1. 三条不可动摇的铁律

1. **默认私有。** 任何数据的默认 `visibility = private`。共享是显式动作，不是默认状态。
2. **记忆永不出实例。** 跨实例只交换**事件和任务**，绝不同步 M2 长期记忆。
   你的偏好、你对客户的判断、你的实体档案，只存在于你自己的服务器上。
3. **私人域零外泄。** 看牙、给家人带东西、体检、家庭安排——凡是与工作无关的，
   标题、地点、时间、参与人、备注，一个字节都不出实例。
   不共享内容，也不共享"这个时段忙"这种元信息（见 §5 的排期方案）。

---

## 2. 方案选型

**已定：纯联邦直连。** 部署前提是用户的服务器有公网 IP，实例之间通过开放协议直接通信，
数据只在双方服务器之间流动。

| 方案 | 评价 |
|---|---|
| 中心化协作服务器 | **否决**。与"自部署"的初衷直接矛盾，我们会成为最大的隐私风险点 |
| **纯联邦直连** | **采纳**。不引入任何中间方 |
| 密文中继兜底 | **不做**。前提已明确要求公网 IP，为 NAT 场景增加中继属于过度设计 |

协议规范应当公开，允许第三方实现兼容端点。理由和第三方市场源一样：
自部署用户不接受被单一实现绑定，我们自己也就不再是单点信任。

### 代价：每个实例都是暴露在公网的服务端点

这是这个选择的直接后果，必须在实现里对冲：

- 联邦端口**默认只接受已建立关系的公钥签名请求**，陌生来源在握手前就拒绝
- 唯一的例外入口是"接受好友邀请"，且必须携带有效的一次性 nonce
- 独立限流与连接数上限，防止被当成 DDoS 放大器
- 协议表面积尽量小：只暴露必需的几个端点，不复用主 API 的路由
- 联邦端口与 App 的 BFF 端口分离，出问题可以单独关停

## 3. 身份与建立关系

### 3.1 实例身份

- 每个实例启动时生成一对长期密钥（Ed25519），指纹即实例 ID。
- 用户身份 = `别名@实例指纹`，别名可改，指纹不可改。
- 私钥用用户主密码派生的密钥加密后落盘，不明文存储。

### 3.2 加好友

```
A 生成一次性邀请（含 A 的公钥、可达地址、短时效 nonce）
  → 二维码 / 邀请码，通过任意带外渠道给 B
  → B 扫码，向 A 发起握手（B 的公钥签名 nonce）
  → A 在 App 上确认「是 B 吗」          ← 人工确认，不可省
  → 双方各自落库对方的公钥与地址，关系建立
```

**必须有人工确认这一步**。自动接受好友请求 = 把攻击面直接开给互联网。

### 3.3 圈子（Circle）

好友可分组：`同事`、`客户`、`家人`、`项目A小组`。
可见性授予的粒度是圈子，不是单个好友——否则用户管不过来。

---

## 4. 可见性模型

### 4.1 域（Domain）是第一决定因素

**每条事件、任务、日程都必须归属一个域，域决定默认可见性，而不是反过来。**

| 域 | 例子 | 默认 |
|---|---|---|
| `personal` 私人 | 看牙、给表姐带手表、家庭聚餐、体检 | **永不进入任何共享通道** |
| `work` 工作 | 客户会议、项目节点、出差、交付 | 可共享，具体给谁由圈子决定 |
| `mixed` 混合 | 用公司预算给客户送礼、周末的工作应酬 | 按 `personal` 处理，逐项由用户放行 |

**分类不确定时一律按 `personal` 处理。** 分错方向的代价是不对称的：
把工作事项误判为私人，只是少共享一次；把私人事项误判为工作，是隐私事故。

「和客户吃饭算工作还是私人」这类模糊情形不靠 AI 拍脑袋——先落到 `mixed`（等同私人），
AI 可以在 App 里建议改域，**用户点头才生效**。

### 4.2 可见性字段

`visibility` 是**数据模型的一等字段**，不是事后加的过滤逻辑。任务、事件、日程、
实体、附件都带这个字段。

| 值 | 含义 |
|---|---|
| `private` | 默认。永不出实例 |
| `circle:<id>` | 对指定圈子可见 |
| `user:<friend_id>` | 对指定好友可见 |

判定顺序：

```
域约束（personal 一律 private，不可被覆盖）
  > 用户显式设置
  > 标签推断（privacy:敏感 → private）
  > 类型默认
```

**域约束排在用户显式设置之前**：私人域的东西要共享，必须先改域，再改可见性。
两步操作是刻意的——防止一次误点就把私人内容发出去。

**AI 可以建议改域或改可见性，但不能自己改。** 任何缩小隐私范围的变更都必须用户确认。

### 4.3 出站过滤器（Egress Filter）

所有外发数据**必须**经过唯一的出站过滤器，不允许任何模块绕过直接发包：

```
待外发对象
  → 可见性检查（对方是否在授权范围内）
  → 字段级裁剪（只保留该可见性等级允许的字段）
  → 敏感标签扫描（残留的 privacy:敏感 字段 → 阻断并告警）
  → 记忆泄漏检查（内容中是否夹带了 M2 记忆片段 → 阻断）
  → 签名
  → 经 TLS（公钥指纹钉住）发送
```

记忆泄漏检查这一步很关键：AI 生成的文案里可能无意带出记忆内容（"张总海鲜过敏所以改了餐厅"
这句话发给项目组，就泄露了客户的健康信息）。**外发文本要过一遍记忆泄漏检查**。

## 5. 可共享的对象

| 对象 | 说明 | 默认 |
|---|---|---|
| **工作事件** | 会议、里程碑、交付节点、共享待办 | 需显式共享 |
| **任务协作** | 委派任务给好友、联合任务的状态同步 | 需显式共享 |
| **排期应答** | 对时间提议回复接受/建议改期，**不暴露忙闲位图** | 对已加好友默认开启 |
| **共享实体** | 共同客户的**工作属性**（对接人、产品线） | 需显式共享，且**逐字段授权** |
| **free/busy 位图** | —— | **不做**，被排期应答取代 |
| **长期记忆** | —— | **永不共享，无开关** |

### 关于排期：用"提议—应答"取代忙闲共享

常规做法是共享 free/busy 位图，但那会泄露作息规律、出差频率、私人时段的密度。
在联邦架构下有更好的做法——**决策留在本人实例上**：

```
对方助手  →  「提议周三 15:00 开会，1 小时」
我的助手  →  本地看到我的全量日程（含周三下午看牙，personal 域）
          →  回「该时段不方便，建议周四 10:00 或周三 17:00」
```

对外只输出**结论**，不输出**依据**。对方永远不知道我周三下午在干什么，
甚至不知道我是有事还是单纯不想开会。

好处：

- 零信息泄露，且不需要"时间窗""粒度"这类必然漏信息的折中参数
- 私人日程天然参与排期决策，不需要为它开任何共享开关
- 应答里可以带上偏好（"我不想在周五下午开会"），这是位图表达不了的
- 可以直接由助手自动完成协商，用户只看结果

代价：多一轮往返。对个人协作场景完全可接受。

**注意**：应答本身也会泄露微弱信息（对方可以反复提议来探测你的空闲分布）。
所以要有频率限制：同一好友短时间内的提议次数设上限，超限后只回"请直接沟通"。

### 关于共享实体

共同客户的档案共享**风险比看上去大**。"张总海鲜过敏"是健康信息，
"张总喜欢被叫张总"是无害的工作信息。所以**逐字段授权**，不能整体共享实体。
默认只允许共享 `domain:工作` 且非 `privacy:敏感` 的属性。

## 6. 传输协议

### 6.1 消息信封

```
{
  to:        接收方实例指纹
  from:      发送方实例指纹
  msg_id:    幂等去重用
  ts:        时间戳（防重放）
  payload:   明文 JSON（传输由 TLS 保护）
  sig:       发送方私钥对整个信封的签名
}
```

- 传输走 HTTPS，双方**用已交换的公钥指纹钉住**，不依赖公共 CA
  （自部署环境下公共 CA 链条不可靠，且指纹是加好友时带外确认过的）。
- **没有中继，所以不需要再套一层端到端加密**。TLS 负责传输机密性，
  签名负责来源真实性与不可否认。少一层加密就少一层密钥管理。
- 签名不能省：它是审计链的依据，也是离线队列重投时校验完整性的手段。

### 6.2 离线与最终一致

对方实例可能关机（个人服务器不保证 7×24）。所以：

- 所有跨实例操作都是**异步消息**，不做同步 RPC
- 本地先落库，发送队列带指数退避重试
- 幂等键去重，允许重复投递
- 长期不可达 → App 提示用户

### 6.3 共享对象的所有权

**单一 owner 制**：共享事件永远有且仅有一个 owner 实例，只有 owner 能修改。
其他人提交的是**提议**，owner 接受后广播新版本。

这样彻底回避分布式冲突合并，代价是协作稍显笨拙。对个人协作场景是划算的。

---

## 7. 撤回与删除的诚实告知

数据一旦发到对方服务器，**我们无法真正收回**。撤回请求只是发一条
"请删除"的消息，对方实例是否照做取决于对方。

这一点必须**在 UI 上明确告诉用户**，不能用"已撤回"这种误导性文案。
正确的说法是"已请求对方删除"。

---

## 8. 与安全模型的关系

好友实例是**独立的信任域**，不是自己人。收到的跨实例数据：

- 信任等级为 `friend`，**低于** 用户本人和权威连接器
- **绝不能作为指令**：好友发来的事件描述里若含"忽略之前的指示"，必须当作纯文本
- 不能直接写入 M2 长期记忆，只能作为记忆候选进入写入管线

详见 `安全模型.md` §3 信任等级。
